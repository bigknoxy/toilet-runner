World-moves-to-player

The world translates toward the player on +Z; the runner never leaves the origin. This keeps coordinates small and avoids float precision drift on long runs. Track segments spawn ahead at roughly -80Z and are recycled once they pass +20Z. 

graph LR
  A[Spawn ~ -80Z] -->|world moves +Z| B[Player plane at 0Z]
  B -->|passes runner| C[Despawn ~ +20Z]
  C -->|pool recycle| A

ScreenManager owns the stack; GameState (src/core/GameState.ts) is the enum. Pause is the one binding that works outside active play, so InputManager handles it before the gameplay-input gate.

Obstacle types

Obstacle kinds live in src/game/ObstacleTypes.ts. Two ship today; the rest are declared but unused.

TypeHitbox half-extents (W x H x D)Answer
POOP0.5 x 0.8 x 0.7 at y 0.3jump or change lane
BARRIER_HIGH1.2 x 1.6 x 0.35 at y 1.5lane change only

The jump apex puts the player mesh at GROUND_Y + JUMP_HEIGHT = 3.0, so its underside reaches 2.6. A barrier top sits at 3.1 and therefore cannot be cleared at any point in the arc. That is what keeps three-lane movement mattering instead of while (true) jump(). Collision half-extents are selected by type in CollisionSystem.halfExtentsFor() and mirrored by the mesh built in ObstacleManager.createBarrierGroup(), so the silhouette matches the hitbox.

Performance design

PerformanceManager measures the device at startup and picks a tier. Everything downstream (particle budgets, post-processing, pixel ratio) reads from the tier. There is no user-agent sniffing anywhere in the path: a phone is graded on what it renders, not on what its UA string says it is.

The boot benchmark draws a rotating TorusKnot at a fixed 512×512 with the same MeshLambertMaterial + HemisphereLight setup the game shades with. Warm-up frames run first, then a timed loop, with gl.readPixels() before and after to force the GPU to drain — without that sync point the loop only measures how fast JS can queue commands, not how fast the GPU executes them. The resulting FPS is normalised by the device's real pixel load (viewport × devicePixelRatio²) to estimate native FPS, the same approach detect-gpu uses. The whole benchmark is budgeted at 250 ms.

Players can override the whole thing: PerformanceManager.setPreference() pins a tier and disables adaptation, persisted under toiletRunner_quality (a key separate from the unified stats blob, because a tier has to be chosen before StatsManager has loaded).

Adaptive quality

A boot benchmark can only guess. A phone that benchmarks well still throttles when it warms up, and a desktop is fine until another tab wants the GPU. AdaptiveQuality watches the frames actually delivered during PLAYING and corrects the guess at runtime. Hysteresis keeps it from oscillating:

TransitionThresholdWindow
Downgradeavg < 45 FPS3 s
Upgradeavg > 58 FPS8 s
Cooldown after any change—5 s

Upgrades need a longer look than downgrades: being briefly too conservative costs some sparkle, being briefly too ambitious costs frames mid-run, which is what a player actually notices in a reaction-time game. The boot verdict is the ceiling — adaptation can recover ground it gave up but never promote a device past what it measured. Frames longer than 0.25 s (tab-switch, GC pause) are discarded rather than counted, so one hitch cannot drop everyone's quality. Telemetry is suspended outside gameplay so an idle menu is not mistaken for headroom. A downgrade tears down post-processing; an upgrade does not rebuild it, since recompiling shaders would stall exactly the frames the upgrade was meant to reward.

  • InstancedMesh for track segments, lane lines, and coins. Obstacles are pooled THREE.Groups of 4-6 meshes, not instanced, so the <10 draw call target is aspirational.
  • Object pooling for obstacles; no per-frame allocations in hot loops. Reuse THREE.Vector3/Box3 instances in update().
  • MeshLambertMaterial everywhere, no PBR.
  • Fog hides pop-in at the spawn distance. HORIZON_COLOR (0x4a6d8c) in SceneManager.ts is shared by the fog, the renderer clear colour, and the CSS body background — the renderer uses alpha: true, so any mismatch draws a band across the skyline. Fog range 45-130 keeps obstacles readable from their ~90-unit spawn distance.
  • Delta time capped at 0.1s in GameLoop so a backgrounded tab does not teleport the world on return.

Data and persistence

Everything lives client-side in localStorage under toiletRunner_unifiedData (schema version 2). Legacy per-feature keys are migrated on load. There is no backend, no account, and no network call at runtime.

Security and privacy

ControlStatusNotes
Server-side attack surfaceNoneStatic site on GitHub Pages; no API, no auth, no secrets in the bundle.
Personal dataLocal onlyThe leaderboard name is a free-text string kept in localStorage, never transmitted.
Untrusted input renderingText nodesScore popups and leaderboard rows are set via textContent, not innerHTML.
Third-party runtime codeNoneThree.js is bundled at build time; no CDN, no analytics beacon, no audio files.
TransportHTTPSGitHub Pages serves the site over TLS.
Score integrityNot enforcedScores are client-authoritative by design — the leaderboard is local, so tampering only affects the tamperer.

Observability

No server, so observation is browser-side plus CI:

QuestionHow to check
Does production boot clean?Load the site headed (WebGL is unavailable in headless Chromium) and read the console; expect zero errors.
Which perf tier did a machine pick?PerformanceManager.getTier() in the devtools console.
What is stored locally?JSON.parse(localStorage.getItem('toiletRunner_unifiedData'))
Is a regression covered?bun run test — the suite targets execution-order and state-lifetime bugs tsc cannot see.
